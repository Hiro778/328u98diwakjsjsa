ADMIN CONTROL CENTER — STAGE 10: SETTINGS

GOAL
Implement Stage 10 Admin Settings sebagai tahap terakhir Admin Control Center.

IMPORTANT:
- Stage 1–9 SUDAH PASS. Jangan regress atau refactor ulang fitur tersebut.
- Settings sebelumnya sengaja disabled/LOCKED.
- Audit existing project/schema/settings infrastructure SEBELUM membuat perubahan.
- Jangan mengarang tabel, kolom, RPC, provider, atau konfigurasi yang tidak benar-benar ada.
- Reuse existing infrastructure whenever possible.
- Jangan membuat duplicate settings table jika sudah ada source of truth.
- Settings hanya untuk konfigurasi ADMIN/PLATFORM yang memang aman dikelola dari Admin Control Center.
- Jangan expose secrets/credentials/API keys/private tokens ke browser.
- Jangan membuat UI yang hanya kosmetik tetapi tidak benar-benar persist ke database.

==================================================

==================================================

Audit terlebih dahulu:

1. Existing Supabase tables terkait:
   - platform settings

3. Audit existing AdminLayout Settings navigation.

4. Audit apakah sudah ada:

5. Audit environment variables.
   NEVER move secrets from environment variables into a client-readable settings table.

REPORT PREFLIGHT FINDINGS sebelum implementasi.

==================================================
PHASE 1 — DEFINE SAFE SETTINGS BOUNDARY
==================================================

Hanya expose settings yang memang aman untuk Admin UI.

Potential categories, ONLY if supported by existing architecture:

A. General Platform
- platform name
- support email
- maintenance mode
- announcement/banner configuration

B. Support
- support email
- support availability/configuration
- FAQ/support configuration jika memang sudah memiliki source of truth

C. Feature Flags
- enable/disable feature flags yang memang sudah existing

D. Operational Configuration
- non-secret operational values yang memang sudah digunakan aplikasi

DO NOT expose:
- Supabase service role key
- Gemini/API keys
- Midtrans secret/server key
- OAuth client secrets
- JWT secrets
- database credentials
- webhook signing secrets
- access tokens
- refresh tokens
- private provider credentials

If a setting currently lives in environment variables and is secret,
KEEP IT IN ENVIRONMENT VARIABLES.

==================================================
PHASE 2 — DATABASE
==================================================

If an existing settings table already exists:
- reuse it
- do NOT create a duplicate.

If no suitable table exists and a persistent settings table is genuinely required:

Create ONE minimal platform settings table following actual project conventions.

Requirements:
- UUID primary key
- key/value or typed columns appropriate to actual settings
- timestamps
- unique setting key if key/value architecture is used
- no secrets
- RLS enabled
- only admins can read
- only authorized admin role can mutate
- SECURITY DEFINER RPC where appropriate
- SET search_path = ''
- revoke PUBLIC/anon execution
- authenticated access only
- validate allowed keys server-side
- audit every mutation

Do not use localStorage as the source of truth.

==================================================
PHASE 3 — ADMIN SETTINGS SERVICE
==================================================

Create centralized service if needed:

src/lib/adminSettingsService.js

Requirements:
- getSettings()
- getSetting()
- updateSetting()
- updateSettings() if bulk update is actually needed
- normalize DB errors
- never return secrets
- never log secrets
- enforce admin authorization through server-side RPC/RLS

Follow conventions established by:
- adminUserService
- adminSubscriptionService
- adminAiUsageService
- adminSupportService
- adminAuditLogService

Do not bypass the service layer with scattered Supabase calls.

==================================================
PHASE 4 — SETTINGS UI
==================================================

Enable:

/admin/settings

Use existing AdminLayout.

Dark Admin Control Center design consistent with Stage 1–9.

UI should include only settings actually implemented.

Required UX:
- loading skeleton
- empty state if applicable
- error state + retry
- save button
- saving state
- success feedback
- validation errors
- unsaved changes protection if multiple editable fields exist
- responsive layout

For destructive/high-impact settings:
- confirmation modal
- explicit warning
- require confirmation before mutation

Do NOT create fake toggles that do nothing.

==================================================
PHASE 5 — AUDIT LOG INTEGRATION
==================================================

Every successful settings mutation must create an entry in:

public.admin_audit_logs

Use existing audit infrastructure from Stage 9.

Examples:

SETTINGS_UPDATED
FEATURE_FLAG_CHANGED
MAINTENANCE_MODE_CHANGED

Use existing audit conventions instead of inventing incompatible structures.

Never place secrets in audit metadata.

==================================================
PHASE 6 — SECURITY TESTING
==================================================

Create:

src/__tests__/admin_settings.test.js

Must test:

1. /admin/settings protected by RequireAdmin
2. non-admin cannot read settings
3. anonymous cannot read settings
4. non-admin cannot mutate settings
5. admin can read settings
6. authorized admin can mutate allowed settings
7. invalid setting key rejected
8. invalid value rejected
9. secret-like setting rejected/not exposed
10. IDOR protection
11. audit log generated after mutation
12. audit metadata contains no secrets
13. Settings navigation enabled
14. Stage 1–9 routes remain intact
15. Settings does not mutate subscriptions/payments/users/businesses
16. persistence survives fresh client/reload

If SUPER_ADMIN-only mutations exist, test ADMIN vs SUPER_ADMIN explicitly.

==================================================
