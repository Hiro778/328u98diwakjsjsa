ADMIN CONTROL CENTER — STAGE 9
AUDIT LOGS

OBJECTIVE:
Implement Admin Audit Logs menggunakan infrastructure audit yang SUDAH ADA.

HARD RULE:
Audit existing schema/code FIRST.
JANGAN membuat tabel audit_logs baru jika public.admin_audit_logs sudah ada.
JANGAN menduplikasi audit infrastructure.

==================================================
1. PREFLIGHT
==================================================

Inspect actual:

- public.admin_audit_logs
- existing migrations
- existing audit RPCs/functions
- existing audit inserts
- RLS
- indexes
- foreign keys
- existing admin services

Identify exactly which actions currently generate audit logs.

Especially verify audit coverage for:

- user suspend
- user unsuspend
- user ban
- user unban
- user soft delete
- subscription cancellation
- business/admin mutations
- support mutations
- payment/admin mutations
- credit/admin mutations if applicable

Do not invent actions that do not exist.

==================================================
2. ACTUAL SCHEMA
==================================================

Document actual columns:

- id
- actor/admin identity
- action
- target/entity
- target ID
- reason
- metadata/details
- timestamp

Use exact existing names/types.

If schema differs, adapt implementation to actual schema.

==================================================
3. ADMIN PAGE
==================================================

Create/enable:

/admin/audit-logs

Use existing AdminLayout patterns.

Sidebar:

Audit Logs

must become active.

Future Settings remains disabled until Stage 10.

==================================================
4. READ-ONLY
==================================================

Audit Logs page is READ-ONLY.

Admin UI must NOT provide:

- edit
- delete
- clear logs
- truncate
- bulk delete

Audit history must be append-only from the admin UI.

==================================================
5. LIST UI
==================================================

Provide:

- timestamp
- admin/actor
- action
- target type
- target ID
- reason where available
- concise details

Use responsive dark UI consistent with existing Admin Control Center.

Add:

- loading skeleton
- empty state
- error state
- retry
- pagination

Do not load unlimited audit rows into browser.

==================================================
6. FILTERS
==================================================

Filters should execute server-side.

Support only filters supported by actual schema/data:

- action
- actor/admin
- target/entity type
- date range
- search
- pagination

Do not invent filters that require nonexistent columns.

==================================================
7. SEARCH / SORT
==================================================

Search must be DB-side.

Sort at minimum:

- newest first
- oldest first

Pagination must be DB-side.

No fetching entire audit table and filtering in React.

==================================================
8. DETAIL VIEW
==================================================

Allow opening an audit event.

Show safe structured details:

- timestamp
- actor
- action
- target
- reason
- metadata/details

If metadata contains sensitive data:

sanitize/redact before returning to frontend.

Never expose:

- passwords
- auth tokens
- API keys
- server keys
- cookies
- authorization headers
- payment secrets

Do not blindly render raw JSON if it can leak credentials.

==================================================
9. SECURITY
==================================================

Admin Audit Logs must be server-side protected.

Use:

is_admin()

and existing admin RPC pattern.

Verify:

- anonymous cannot read
- normal authenticated user cannot read
- non-admin cannot call admin RPC
- admin can read allowed audit logs
- IDOR cannot retrieve unauthorized audit data

Do not rely on frontend role checks.

Do not use localStorage as authorization.

==================================================
10. SUPER ADMIN
==================================================

Audit whether SUPER_ADMIN has any special audit permissions.

Do NOT invent special behavior.

If existing schema permits all admins to read logs, preserve that.

Mutating/deleting audit logs should remain unavailable.

==================================================
11. AUDIT COMPLETENESS
==================================================

Do NOT rewrite every existing mutation unless the preflight proves a critical admin action is currently missing audit logging.

If missing audit coverage is discovered:

- identify exact mutation
- add audit logging using existing infrastructure
- keep mutation atomic where possible
- do not create duplicate audit entries

Prioritize existing sensitive admin actions.

==================================================
12. SERVICE
==================================================

Create a centralized service if one does not already exist:

adminAuditLogService.js

It should handle:

- list
- filters
- pagination
- detail
- error normalization

Do not expose raw Supabase errors.

Reuse existing admin service conventions.

==================================================
13. RPC
==================================================

If existing RPC is insufficient, create the MINIMUM required RPC(s).

SECURITY DEFINER
SET search_path = ''

Must verify:

public.is_admin()

Revoke public/anon EXECUTE.

Grant only required authenticated/service_role access according to existing project pattern.

Do not expose unrestricted SQL/RPC access.

==================================================
14. TESTS
==================================================

Create focused tests covering:

1. admin can list audit logs
2. admin can paginate
3. admin can filter action
4. admin can filter actor
5. admin can filter date
6. search works server-side
7. sorting works
8. detail works
9. anonymous denied
10. non-admin denied
11. IDOR denied
12. secrets are not exposed
13. audit logs are read-only
14. existing sensitive mutations still create audit records
15. no duplicate audit entries

Run existing Admin Stage 1–8 regression.
